# 当前板编码器与 CAN 检查（2026-10-31）

后续修复：CAN 初始化失败的停机重试已经实现、烧录，并通过实板模拟失效恢复及桌面 STOP/9 参数读取验证，详见 [CAN 自动恢复记录](CAN_INIT_RECOVERY_20261031.md)。该次复测编码器为 NO_MAGNET，角度暂时无效。以下为修改 CAN 前的历史排查记录。

修改前状态：用户修复外部上拉后，编码器持续有效；CAN 在 PCAN 就绪后复位 MCU 已恢复双向通信，约 8 秒收到 2168 帧，其中包含 STOP 执行成功应答、状态/诊断及遥测。该阶段诊断故障为 0，bus-off/error-passive 均为 false。证据更支持启动初始化失败及缺少重试的问题，不能将此前无反馈直接判定为芯片损坏。

用户此前要求启用内部上拉，已修改驱动并烧录校验。约 12.6 秒的 100 次停机快照均有效；观察到的新角度时间戳间隔中位约 2.63 ms（约 380 Hz）。详见 [软件上拉版本记录](I2C_PULLUP_20261031.md)。下文保留各阶段的定位过程。

本记录对应用户更换后要求检查的当前板，现场日志后缀为 `20261031-b`；不要与上一块板的检查混用。修改前 Flash 的前 32972 字节与当时 Release BIN 完全相同。以下初步排查阶段没有烧录；所有阶段均未发送电机运动指令。

## 编码器结果

原固件运行时取得 40 次状态快照，均为 `BOARD_ENCODER_BUS_ERROR`，`sensor_valid=false`。PB6/SCL 为高，PB7/SDA 为低。电机始终 STOP，驱动关闭、PA4 EN 为低。

随后暂停 CPU，冻结采样定时器及看门狗，保持 EN 低，释放两根开漏线。SDA 仍为低；发送 9 个恢复时钟及 STOP 后仍低。因此此时的低电平不是正常传输过程中恰好采到的数据位。

仅将 PB7 改为输入弱上拉并保持 ODR=1 后，SDA 能变高。通过 SWD 操作 GPIO，使用慢速时钟，并在释放 SDA 时临时启用内部弱上拉，可得到 AS5600 应答及以下读数：

| 项目 | 实测 |
| --- | --- |
| STATUS | 连续 3 次为 `0x67`；仅解释有效状态位，`MD=1, ML=0, MH=0` |
| RAW ANGLE | `0x0752`，1874 计数，约 164.7° |
| AGC | 72 |
| MAGNITUDE | 2088 原始计数，不换算为 mT |

这说明当前板的磁铁被检测到，弱磁/过强标志均未置位，芯片在该临时测试条件下能够通信。恢复原 GPIO 配置后，运行固件再次报告 BUS_ERROR。

排查重点是 SDA 外部上拉电阻、其 3.3 V 端及相应连接，以及正常速率下的信号质量。测试同时改变了上拉方式和通信速度，不能仅凭这一步断言某一只电阻已损坏，也未验证整圈角度精度或电流闭环。优先核查原理图中 U2 的 6 脚 SDA 上拉链路。

## CAN 结果

PCAN-USB 已识别，PCAN_USBBUS1 可按 1 Mbps 打开。首次接收窗口 5 秒内无 CAN 帧；板上 `BoardCanStatus.initialized=false`。

在 PCAN 接收窗口开启后，对已核对为上电停机的 Release 固件执行一次 MCU 复位。此后 CAN 初始化标志变为 true，但出现 error-passive，接收错误计数为 255，最近错误码为 1；8 秒接收窗口仍为 0 帧。用户随后确认，此阶段只有 DAPLink 供电，未接主电源；不能将这一阶段的错误归因为 CAN 芯片损坏。

用户接上主电源后，再次打开 PCAN 接收窗口并复位 MCU。CAN 初始化成功，复位约 1 秒后发送错误计数为 128、接收错误计数为 0、最近错误码为 3（ACK 错误）；约 2 秒时保持相同错误状态，没有成功发送计数。PCAN 8 秒窗口仍为 0 帧。当前排查重点为 CANH/CANL/GND 实际接线、收发器供电及终端匹配，尚未确认具体物理原因。编码器原配置仍为 BUS_ERROR，电机 STOP/EN 低。

通电后复测证据：`encoder-can-20261031-b-powered.log`、`encoder-can-20261031-b-powered-reset.log`、`pcan-receive-20261031-b-powered-reset.json`。用户的 CAN 信号线接法正在等待核对。

用户再次要求复测时（日志前缀 `retry-20261031-111801`），只接收窗口仍为 0 帧。随后使用项目协议编码器生成 STOP，向节点 1 的标准 ID `0x201` 排入一帧 `A1 00 01 00 00 00 00 00`；PCAN 随后报告 bus-off，测试立即结束并关闭接口，没有排入任何运动指令。同期 SWD 快照中，板端 CAN 接收计数和成功发送计数均始终为 0，原固件编码器状态仍为 BUS_ERROR，电机 STOP、驱动关闭。这表明本轮停机握手也没有取得有效接收或执行确认，仍需排查物理链路和收发器供电。

## 外部上拉修复后的 CAN 恢复

用户报告上拉已修复后（日志前缀 `can-after-pullup-20261031-113834`），现场 Flash 与软件上拉版 Release BIN 的 33464 字节完全一致。编码器持续 OK/有效，但板上 CAN 初始化标志为 false，收发计数为 0。此时主循环正常推进，问题并非整个 MCU 停住。

当前 `main.c` 只在启动时调用一次 `BoardCan_Init()` 并忽略失败返回值；失败后主循环仍运行，协议不断尝试发送却不会重新初始化外设。现场 CAN 位时序已写入而初始化失败，与正常供电/总线准备完成前未能退出初始化的情况相符；具体启动电压及 RXD 波形没有测量，不能进一步断言某个器件或电源时序细节。

保持 PCAN_USBBUS1 / 1 Mbps 接收窗口开启后复位 MCU，CAN 初始化成功。约 1.2 秒时板端有效接收计数为 2、成功发送计数为 382、错误计数为 0。约 8 秒共收到 2168 帧：ACK `0x381` 1 帧、状态 `0x181` 723 帧、诊断 `0x281` 722 帧、遥测 `0x581` 722 帧。解码得到 STOP/sequence=2 执行 OK、故障为 0；最新诊断为已初始化、非 bus-off、非 error-passive，编码器有效、驱动关闭。接收脚本本身未下发应用帧，STOP 应答来自前序停机测试命令。没有发送启动/对齐/电流指令。

本阶段验证说明 MCU、收发器和实际 CAN 链路能够完成有效的双向通信；无法由此前无反馈推断芯片损坏。当时尚未修改初始化失败后的恢复逻辑；后续实现及验证见本文开头链接。

## 结束状态与证据

上述初步排查结束时，临时 GPIO 配置及 DBGMCU 寄存器已恢复。用户要求修改固件后，内部上拉已随新驱动保留生效，不再是一次性的调试器配置。最终检查均为 STOP、驱动关闭、EN 低；OpenOCD 和临时 PCAN 接收进程已退出。只有软件上拉版的有效数据用于后续角度观察。
